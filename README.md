# Как запустить наш проект (и что внутри)

Публичный стенд работает за TLS-терминацией (Caddy):
1) веб-интерфейс Заявителя — `https://<адрес стенда>/`
2) веб-интерфейс Сотрудника — `https://<адрес стенда>:8443/`

Если для стенда используется домен, Caddy автоматически выпускает сертификат Let's Encrypt; для голого IP — самоподписанный сертификат (браузер покажет предупреждение, это ожидаемо для демо-стенда).

Если вы склонировали репозиторий, то всё, что нужно сделать для запуска — это выполнить пару команд в терминале:

```bash
git clone https://github.com/Antosha122/otklik.git
```
```bash
cd otklik
```
```bash
cp .env.example .env
```
```bash
docker compose up -d --build
```

И всё, через минуту у вас работает три контейнера. Первый — база данных PostgreSQL (версия 16), она поднимается с пользователем `otklik` и паролем из `.env`. Второй — само приложение на Go, которое слушает два порта: `8080` для заявителей (публичная часть) и `8081` для сотрудников (операторы, эксперты, админ); наружу эти порты не публикуются — только с localhost. Третий — Caddy: TLS-терминация, шифрует трафик и проксирует его в приложение. При первом запуске автоматически накатываются миграции и создаются начальные данные — категории и тестовые пользователи, но только если база данных пустая. Это удобно, не надо ничего настраивать руками.

Проверить, что всё работает, можно простым `curl http://localhost:8080/api/health` (порт приложения виден с localhost) или `curl -k https://localhost/api/health` (через Caddy). Если ответит `ok` — значит, порядок.

Дальше открываете в браузере:

- `https://localhost/` — это страница для заявителя: тут можно создать обращение, потом зайти по трек-номеру и общаться с экспертом в чате, который сам обновляется.
- `https://localhost:8443/` — страница для сотрудников, тут логинитесь под демо-учёткой и попадаете в свою рабочую зону.

Для локальной разработки без TLS порты приложения доступны напрямую: `http://localhost:8080/` и `http://localhost:8081/` (в `.env` при этом должен быть `COOKIE_SECURE=0`).

Если хотите остановить — `docker compose down`. Данные при этом сохраняются в volume, так что при следующем запуске они останутся.

**Важно:** пароль БД задаётся только при создании volume, но для его смены не нужен `down -v` (этим вы удалите все данные). Правильный способ — сменить пароль внутри работающей базы и в `.env`, затем пересоздать только приложение:

```bash
docker compose exec -T db psql -U otklik -d otklik -c "ALTER USER otklik WITH PASSWORD 'новый_пароль';"
# затем впишите тот же пароль в POSTGRES_PASSWORD в .env и:
docker compose up -d app
```

## Эксплуатация: бэкапы, хранение данных, логи, CI

### Бэкапы и восстановление

Четвёртый контейнер `db-backup` раз в сутки делает `pg_dump` в кастомном формате (`-Fc`, со сжатием) в volume `backups`, хранит последние `BACKUP_KEEP` копий (по умолчанию 14). Первый бэкап делается сразу при старте контейнера — так проще проверить, что всё работает:

```bash
docker compose ps db-backup                       # должен быть запущен
docker compose exec db-backup ls -lh /backups    # список копий
```

Проверка восстановимости (обязательная часть регламента — делайте её хотя бы раз после развёртывания):

```bash
# копируем свежий бэкап и разворачиваем его в отдельную базу на том же сервере
docker compose exec db-backup sh -c 'pg_dump -Fc otklik > /backups/verify.dump'
docker compose exec -T db psql -U otklik -d postgres -c "CREATE DATABASE otklik_verify;"
docker compose exec db-backup pg_restore -U otklik -d otklik_verify --no-owner /backups/verify.dump
docker compose exec -T db psql -U otklik -d otklik_verify -c "SELECT count(*) FROM appeals;"
docker compose exec -T db psql -U otklik -d postgres -c "DROP DATABASE otklik_verify;"
```

Полное восстановление из бэкапа (аккуратно: затирает текущую базу):

```bash
docker compose stop app
docker compose exec db-backup pg_restore -U otklik -d otklik --clean /backups/otklik-ГГГГММДД-ЧЧММСС.dump
docker compose start app
```

Бэкап-файлы лежат в docker volume на том же сервере. Для защиты от потери самого сервера периодически копируйте их наружу (например, `docker compose exec db-backup cat /backups/<файл> > локальная_копия.dump` или rsync volume на резервную машину).

### Срок хранения данных (retention)

Обращения содержат чувствительные данные детей, поэтому копиться вечно они не должны. Джанитор раз в час удаляет терминальные обращения (завершено / отклонено / закрыто без ответа), не обновлявшиеся дольше `RETENTION_DAYS` дней (по умолчанию 730), вместе с чатом, событиями, записями о вложениях и файлами вложений на диске. `RETENTION_DAYS=0` отключает удаление. При остановке сервера джанитор завершается корректно: main ждёт его (WaitGroup, до 15 с), а начатая чистка файлов не прерывается сигналом — осиротевших каталогов вложений не остаётся.

### Логи

Приложение пишет структурные логи в stdout в формате JSON (`LOG_FORMAT=text` для локальной отладки) — их собирает Docker, дальше любой лог-коллектор. Каждый запрос логируется с уникальным `request_id` (он же возвращается клиенту заголовком `X-Request-ID`), методом, путём, кодом, длительностью и адресом. Внутренние ошибки логируются с тем же `request_id` — по нему инцидент трассируется от жалобы пользователя до строки кода.

### CI

GitHub Actions (`.github/workflows/ci.yml`) на каждый push/pull_request: сборка и юнит-тесты Go, интеграционные тесты против чистого PostgreSQL 16 (сервис в раннере), тесты фронтенд-ядра на Node (`npm test`). Мерж без зелёного CI не имеет смысла.

## Тестовые учётные записи (создаются при первом старте)

У всех демо-пользователей пароль одинаковый — он задаётся переменной `SEED_DEFAULT_PWD` при первом старте. Явного дефолта в коде нет: если переменная пуста, приложение генерирует случайный пароль и печатает его в лог один раз (при первом старте). При первом входе система обязывает сменить этот пароль: пока он не сменён, весь API сотрудника отвечает `403 password change required`, кроме эндпоинта смены пароля.

Вход только на порту 8081, на вкладке «Сотрудник». Вот кто у нас есть:

- **Оператор** — логин `operator`. Он видит очередь новых обращений, может назначать эксперта, менять приоритет и категорию, отклонять, завершать или закрывать без ответа. Также может возвращать на доработку. Ему доступна аналитика только по своим действиям.
- **Эксперты**: у нас есть несколько ролей. Психологи — `psychologist1` и `psychologist2`, юрист — `lawyer1`, конфликтолог — `conflictolog1` (но если база уже была создана до переименования, то конфликтолог может остаться под старым логином `mediator1` — мы это учли в миграциях). Эксперт работает только с теми обращениями, которые ему назначены, может взять их в работу, задавать уточняющие вопросы, готовить рекомендации, запрашивать передачу другому специалисту или подключать соисполнителей. Также у него есть внутренние заметки и аналитика по себе.
- **Администратор** — логин `admin`. У него доступ к админ-панели: дашборд с графиками (динамика обращений по дням, статусы, специальности, топ категорий) и KPI, управление пользователями, категориями и правилами маршрутизации, жалобы. CSV-выгрузки с фильтрами — из его личного кабинета. Он может менять статус, приоритет и исполнителя у любого обращения, но при этом обязательно указывает причину, и всё пишется в журнал. При этом админ не видит переписку и заметки, и не может закрывать обращения — это не его задача.

Ещё есть социальный педагог, но он не создаётся автоматически на старой базе (сиды только на пустой), так что если он нужен, его придётся добавить вручную через админку.

## Что умеет наш веб-интерфейс

Мы сделали встроенный одностраничный интерфейс (без внешних зависимостей, он вшит в бинарник через `go:embed`). Он работает и на 8080, и на 8081, но в зависимости от порта показывает разное.

На порту 8080 (заявитель) — первая страница объясняет, что это за сервис, почему он безопасен и что происходит после отправки. Есть две явные кнопки: «подать обращение» и «проверить статус». При подаче можно выбрать категорию или написать свободно, причём пункт «Не знаю, как назвать» есть и в списке категорий, и отдельным чекбоксом. Дальше идут уточняющие вопросы с вариантами ответов (но они не обязательные), можно приложить до 5 файлов по 10 МБ, при этом сервер вырезает EXIF и геолокацию. После отправки выдаётся трек-номер — его надо сохранить, восстановить нельзя. Потом по этому номеру можно зайти в чат, где видно статус обращения и можно переписываться с экспертом. Интерфейс дружелюбный, без красных рамок и предупреждений об ответственности, тон меняется в зависимости от типа заявителя: со школьником — на «ты», с родителем или педагогом — на «вы». В конце, когда эксперт даст рекомендации, заявитель может нажать «помогло» или «не помогло» — если не помогло, обращение возвращается оператору для пересмотра.

На порту 8081 (сотрудники) — тут уже сложнее. Оператор видит очередь, может назначать эксперта с учётом подсказки системы, выставлять приоритет и категорию. Если эксперт запрашивает передачу другому специалисту, в очереди появляется бейдж «↔ требуется другой специалист». Эксперт видит только свои обращения, может вести чат и оставлять внутренние заметки (их заявитель не видит), а также управлять статусом. Админ в своей панели видит дашборд с графиками (динамика по дням, статусы, специальности, категории, нагрузка), метаданные обращений с фильтром по статусу и управляет справочниками; выгрузка CSV — из личного кабинета с фильтрами.

Всё обновляется автоматически с интервалом 5 секунд (поллинг), так что сообщения появляются почти мгновенно. При этом если вы печатаете текст, обновление не сбросит ваш ввод.

## Про приватность

Мы с самого начала проектировали сервис с учётом анонимности. Заявитель не регистрируется, не оставляет никаких контактов — доступ только по трек-номеру. Мы даже разделили порты: заявители ходят на 8080, а сотрудники на 8081, чтобы случайно не смешивать контексты.

Трек-номера и сессионные токены хранятся в базе только в виде SHA-256 хешей — если база утечёт, никто не сможет получить доступ к обращениям. Пароли сотрудников хранятся через bcrypt.

Каждая роль видит только то, что ей необходимо: заявитель — минимум (без имён и заметок), эксперт — только свои обращения, оператор — очередь, админ — только метаданные (текст обращения ему не показывается). Вложения тоже обезличены: исходные имена файлов отбрасываются, выдаются как `attachment.bin`, тип проверяется по фактическому содержимому (whitelist MIME), при отдаче ставится заголовок `X-Content-Type-Options: nosniff`. Лимит на файлы — 5 штук по 10 МБ.

Чтобы защититься от перебора, мы поставили ограничения: создание обращений — не больше 5 с одного IP в час, попытки входа по трек-номеру — 20 в час, логин сотрудников — 10 в минуту. Сессии живут 2 часа (можно настроить через `SESSION_TTL_MIN`).

## Как мы сделали трек-номер

Трек-номер — это единственный ключ для заявителя. Он должен быть надёжным, поэтому мы выбрали формат `ОТК-X7KD-R9MF-Q3HP` (12 значащих символов) из алфавита без похожих символов — исключили 0, O, I, L, чтобы не путать при вводе. Генерируется через `crypto/rand`, так что перебор невозможен, плюс rate limit.

Важный момент: номер выдаётся ровно один раз при создании обращения, и мы его не храним в открытом виде — только хеш. Поэтому восстановить номер нельзя, если пользователь его потерял, обращение становится недоступным. Это сознательная жертва ради анонимности.

## Переменные окружения (что можно настроить)

Вот основные параметры, которые вы можете менять:

- `LISTEN_ADDR` — адрес для публичного порта (по умолчанию `:8080`)
- `STAFF_LISTEN_ADDR` — для сотрудников (по умолчанию `:8081`)
- `DATABASE_URL` — строка подключения к БД
- `ATTACHMENTS_DIR` — папка для файлов (по умолчанию `./data/attachments`)
- `SESSION_TTL_MIN` — время жизни сессии в минутах (120)
- `COOKIE_SECURE` — если `1`, то куки только по HTTPS (по умолчанию `1`; для локальной разработки без TLS — `0`)
- `RETENTION_DAYS` — срок хранения завершённых обращений в днях (730; `0` — бессрочно)
- `LOG_FORMAT` — формат логов: `json` (прод) или `text` (локальная отладка)
- `SEED_DEFAULT_PWD` — пароль для демо-пользователей; если пуст — генерируется случайный (печатается в лог при первом старте)
- `BACKUP_KEY` — ключ шифрования ночных бэкапов БД (AES-256-CBC; при утере ключа бэкапы не восстановить)
- `PUBLIC_SITE` — адрес публичного сайта для Caddy (заявители), по умолчанию `localhost`
- `STAFF_SITE` — адрес служебного сайта для Caddy (сотрудники), по умолчанию `localhost:8443`

### Секреты и `.env`

Пароль PostgreSQL и пароль демо-пользователей не хранятся в `docker-compose.yml`: они читаются из файла `.env` рядом с compose-файлом (сам `.env` в git не попадает — он в `.gitignore`). Шаблон — в `.env.example`: скопируйте его (`cp .env.example .env`) и задайте свои значения.

Как сменить пароль PostgreSQL на работающем стенде — см. инструкцию с `ALTER USER` выше в разделе запуска (пересоздавать volume не нужно). На публичном стенде обязательно задайте собственные `POSTGRES_PASSWORD` и `SEED_DEFAULT_PWD`, а также `COOKIE_SECURE=1`.

## Безопасность

- На все ответы (оба порта) ставятся заголовки: `Content-Security-Policy`, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`. `Strict-Transport-Security` добавляется при `COOKIE_SECURE=1` (деплой за TLS-терминацией). Инлайн-скрипты не используются, поэтому CSP для скриптов — строгий `script-src 'self'`.
- Защита от CSRF: все изменяющие запросы (POST/PUT/PATCH) с заголовком `Origin`/`Referer` проходят проверку same-origin; чужой источник получает `403`. Не-браузерные клиенты (curl, мониторинг) работают как раньше.
- Аутентификация — только HttpOnly-куки (`SameSite=Lax`); bearer-токены не выдаются и не принимаются. Токены сессий и трек-номера хранятся в БД только как SHA-256-хеши.
- Сессия заявителя привязана к устройству: в БД хранится SHA-256-хеш User-Agent, и кука, выданная в одном браузере, в другом не работает (подсмотренный экран, пересланный трек-номер или украденная кука сами по себе переписку не открывают — нужен новый вход по трек-номеру, а он под rate-limit). Активной сессии, у которой до истечения осталось меньше половины TTL, токен автоматически ротируется — окно жизни украденной куки ограничено.
- Рейт-лимиты считают адрес клиента по `X-Forwarded-For` только от доверенных (приватных) прокси — Caddy в закрытой docker-сети; подделать заголовок «напрямую из интернета» и обойти лимиты перебора нельзя. Память рейт-лимитера ограничена (периодическая чистка + потолок числа ключей).
- TLS-терминация — Caddy перед приложением: наружу торчат только 80/443/8443, порты приложения (8080/8081) и PostgreSQL (5433) привязаны к `127.0.0.1` хоста. Домены получают сертификат Let's Encrypt автоматически, голый IP — самоподписанный сертификат Caddy.
- Сотрудник может сменить свой пароль: `POST /api/auth/password` с `current_password`/`new_password` (кнопка «Сменить пароль» в панелях). После смены все прочие сессии пользователя инвалидируются, текущая — остаётся.
- Двухфакторная аутентификация (TOTP, RFC 6238) для любой учётной записи сотрудника: включается в личном кабинете (`/profile`): `POST /api/auth/totp/setup` выдаёт секрет для приложения-аутентификатора (Google Authenticator, Aegis, FreeOTP), `POST /api/auth/totp/enable` подтверждает его кодом, после чего вход требует поле `totp_code` (без кода — `401 totp_required`, фронт показывает поле). Отключение — `POST /api/auth/totp/disable` с текущим паролем. Потерян телефон с приложением — 2FA снимает администратор: `DELETE FROM user_totp WHERE user_id = (SELECT id FROM users WHERE login = '...')`. Для админа 2FA настоятельно рекомендуется: это единственная роль с полным доступом к персональным данным.
- Демо-пароль (`SEED_DEFAULT_PWD`) обязательно сменяется при первом входе: пока `must_change_password=true`, API сотрудника закрыт (`403`), фронт сам показывает диалог смены пароля. При каждом входе флаг сверяется с фактом: если пароль уже не демо-пароль (например, хеш меняли вручную), требование смены гасится автоматически — повторных диалогов и «зацикливания» после перезапусков не бывает.

## Что из эндпоинтов есть (кратко)

Публичные (без авторизации):
- `/api/health` — проверка жизни
- `/api/categories` — список категорий
- `/api/intake-questions` — уточняющие вопросы
- `/api/help/crisis` — контакты экстренной помощи
- `POST /api/appeals` — создание обращения (возвращает трек-номер)
- `POST /api/appeals/track` — вход по трек-номеру (устанавливает сессионную куку)

Заявитель (после входа):
- `/api/appeals/me` — статус, описание, рекомендации, чат, история
- `/api/appeals/me/messages` — чтение и отправка сообщений
- `/api/appeals/me/append` — дописать обращение
- `/api/appeals/me/result` — помогло/не помогло
- `/api/appeals/me/feedback` — оценка и комментарий
- `/api/appeals/me/complaint` — жалоба на специалиста
- `/api/appeals/me/attachments` — управление вложениями

Сотрудники (после логина через `/api/auth/login`):
- Оператор: `/api/operator/queue` (очередь новых, с пагинацией `?page=&per_page=` и счётчиком просроченных `overdue_total` по всей очереди), `/api/operator/appeals` (список с фильтрами и пагинацией `?page=&per_page=`), а также действия над конкретной заявкой: назначение, приоритет, категория, отклонение, завершение, закрытие, возврат, ревью кризисной пометки (`POST /api/appeals/{id}/crisis-flag` — снятие ложного срабатывания автодетекта с обязательной причиной, попадает в журнал событий).
- Эксперт: `/api/expert/appeals` (только его заявки, с пагинацией), статусные действия (взять, уточнить, рекомендация, запрос передачи, соисполнители), чат и заметки.
- Админ: `/api/admin/appeals` (с пагинацией и фильтром `?status=`), `/api/admin/users`, `/api/admin/categories`, `/api/admin/complaints`, а также настройки маршрутизации (`/api/admin/settings`). `/api/admin/stats?from=&to=` — дашборд: агрегаты (всего/в работе/срочные/завершено, средние времена), распределения (статусы, типы заявителей, категории, специальности), дневная серия `by_day` (новые/завершённые по дням, до 30 дней) для графика динамики, `expert_limit` и нагрузка `workload` для индикаторов active/limit.
- Все списковые эндпоинты возвращают метаданные страниц: `page`, `per_page`, `total`, `total_pages` (по умолчанию 20 на странице, максимум 100).
- Для всех сотрудников: `/api/profile` (личный кабинет: карточка профиля, персональная аналитика оператора/эксперта, нагрузка эксперта относительно лимита, журнал последних действий), `/api/staff/experts` (список специалистов с нагрузкой), `/api/mystats` (персональная аналитика), `POST /api/auth/password` (смена своего пароля). Страница кабинета — `/profile`, доступна из панелей всех ролей.
- CSV-выгрузка — только из личного кабинета: `/api/export/appeals?from=&to=&status=&priority=&group=&crisis=` (валидация значений — 400). Охват по роли: эксперт — только свои обращения, оператор — только те, где он назначал специалиста или отклонял, админ — все. Файл `appeals-YYYYMMDD.csv` с BOM для Excel; не более 20 000 строк за выгрузку.
- Также есть эндпоинты для присутствия (кто сейчас в карточке и печатает) — `/api/appeals/{id}/presence`, и для аудита — `/api/appeals/{id}/events`.

## Архитектура в двух словах

Код разделён на стандартные слои: `cmd/server` — точка входа, `internal/config` — настройки, `internal/db` — подключение к БД, миграции и сиды, `internal/domain` — бизнес-логика (статусы, трек-номера, кризис-эвристика), `internal/store` — все SQL-запросы, `internal/httpapi` — REST-обработчики, маршруты, аутентификация и проекции данных для каждой роли. Всё просто и прозрачно.
